EC2 Reserved Instance Governance & Recommendation Automation

Use historical demand, existing coverage and eligibility checks to prepare reservation decisions for review.

← All insights

BY PAVAN KUMAR · 29 OCTOBER 2026

A running EC2 instance is an inventory fact. It is not, by itself, a reason to buy a Reserved Instance. This implementation connects the current estate with approximately 90 days of historical usage to identify remaining On-Demand demand after existing Reserved Instance and Savings Plans coverage.

Recommendations only

The documented automation produces reports and an email for governance review. It does not purchase, modify, exchange, list, sell or cancel reservations. Estimated savings are planning inputs, not verified savings outcomes.

The problem: inventory alone is not enough

Across multiple accounts, a current instance list cannot show how consistently workloads ran or how much usage was already covered. The workflow separates discovery, coverage analysis and recommendation generation so reviewers can trace a proposal back to its inputs.

A three-stage workflow

  1. Collect the current EC2 estate

    A Lambda function in a governance account uses cross-account read access to collect running instances. The inventory includes account, Region, instance ID, type, operating system, creation date and normalization units. A CSV is copied to centralized reporting storage in the management/payer account.

  2. Analyze coverage and eligibility

    A second Lambda reads the inventory and queries approximately 90 days of Cost and Usage Report (CUR) data through Amazon Athena. It separates On-Demand, RI-covered, Savings Plans-covered and Spot usage, then produces an instance-level eligibility report.

  3. Prepare reservation recommendations

    A third Lambda groups eligible demand, checks RI Marketplace offerings first, and evaluates AWS Standard Regional one-year No Upfront RIs for the remaining requirement. It produces recommendation and Marketplace-option CSVs, then sends an HTML summary through Amazon SES.

Filter demand before evaluating commitments

The runbook defines the following implementation-specific checks:

  • Exclude instances younger than 30 days and instances without matching historical CUR usage.
  • Remove usage already covered by RIs or Savings Plans; skip instances with no remaining On-Demand compute demand.
  • Exclude Spot, EC2 Mac, Dedicated Host and dedicated-tenancy workloads from this recommendation process.
  • Exclude instances with a type change during the analysis period or a mismatch between the current type and CUR.
  • Exclude non-runtime charges, including data transfer and EBS-optimized charges, from instance running hours.

No minimum monthly cost or 700/720-hour threshold is applied to each individual instance. Eligible usage is aggregated when estimating demand. These are the project's selection rules, not universal AWS eligibility requirements.

Use running hours, not instance counts

The runbook uses a simplified three-month, 720-hour-per-month illustration:

Illustrative demand calculation

2,159.76 On-Demand hours ÷ 3 = 719.92 hours per month, or approximately 1 instance equivalent.
1,080 On-Demand hours ÷ 3 = 360 hours per month, or 0.5 instance equivalent.

An instance equivalent is a demand estimate, not a fractional RI purchase instruction. The 720-hour month is an example assumption; calendar months vary. Before committing, reviewers should also examine hourly overlap, usage variability and expected workload changes. A historical average alone does not establish a continuously utilized commitment.

Apply the right matching rules

The implementation groups Linux/UNIX demand by instance family using normalized units, while Windows demand is grouped by exact instance type. AWS limits instance size flexibility to qualifying regional Linux/UNIX RIs with default tenancy. Review matching attributes, including Region, platform and tenancy, before applying any recommendation.

Regional RIs provide a billing discount; they do not reserve capacity. See the AWS guide to regional and zonal Reserved Instances for scope and size-flexibility rules.

Marketplace first is a project strategy

This workflow looks for suitable Marketplace offerings before considering the one-year AWS fallback. It is not a claim that Marketplace options are always cheaper or suitable. Review the actual remaining term, upfront and recurring charges, matching attributes and forecast demand before accepting a proposal. Availability and pricing need to be checked at decision time.

Make the output useful for review

  • Inventory report: the current organization-wide EC2 estate.
  • Coverage report: instance-level remaining demand and eligibility.
  • Recommendation report: proposed reservations, estimated costs and savings.
  • Marketplace report: candidate offerings for further evaluation.
  • Email summary: a governance-team review entry point.

Keep the decision with accountable owners

The automation ends at reporting. Before any separate purchase action, validate the data period and completeness, confirm workload plans with owners, review existing commitments and approve the proposed term and spend. After an approved purchase, track coverage, utilization and actual cost impact.
